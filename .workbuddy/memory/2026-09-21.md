## 踩过的坑（可复用）

| 坑 | 现象 | 解法 |
|---|---|---|
| Gradle 在受限环境加载 `native-platform.dll` 失败 | `Could not initialize native services` | 换一个全新的 `GRADLE_USER_HOME`；本机用 `--no-daemon` |

| `gdx-backend-android` 是 **AAR** 不是 jar | 直接下 jar 得到 404 | 下 `.aar` 再解出 `classes.jar` 才能用 javac 验证 |
| aapt2 单独跑要求清单里有 `package` 属性 | `must have a 'package' attribute` | AGP 会自动注入；独立验证时用临时副本加 package |

## 收尾：两端产物真的做出来了（同日 18:00 前后）

上一轮停在"三层验证通过、但 APK 没签出来"。这一轮把交付补齐：

### 根因：漏了一个依赖构件

第一次跑桌面 jar 直接崩：

```
java.lang.NoClassDefFoundError: com/badlogic/gdx/utils/SharedLibraryLoader
```

**libGDX 1.13.x 把 `SharedLibraryLoader` 从 `gdx.jar` 拆到了独立构件
`com.badlogicgames.gdx:gdx-jnigen-loader`（1.13.5 → 2.5.2）**。
`GdxNativesLoader` 是 `new SharedLibraryLoader()` —— 编译期无关、运行期才解析的引用，
所以 `javac` 全绿、`gradle build` 全绿、一启动就炸。手抄的 jar 清单必然漏这个。
核对依据：`curl https://repo1.maven.org/maven2/com/badlogicgames/gdx/gdx/1.13.5/gdx-1.13.5.module`。
补齐后还发现桌面端另需 `jlayer-1.0.1-gdx` 与 `jorbis-0.0.17`。

### 决策：构建链不再依赖 Gradle（D31）

Gradle 在这个环境里已经恶化到**连启动都进不去**（`Could not initialize native services`
+ `native-platform.dll.lock 拒绝访问`）。它拦的是调度层，不是编译本身。
所以新增 `tools/*.py`，直连工具链：

```
fetch_libs.py / fetch_natives.py / make_font.py / build_jar.py / build_apk.py / run_smoke.py
```

### 中文字体随包分发（D30）

原方案靠系统字体路径（Windows 硬编码 `C:/Windows/Fonts/*`、Android 猜 `/system/fonts/*`），
不可靠。改成：`make_font.py` 扫全部 `.java` 源码取出用到的字符 → `pyftsubset`
从 Noto Sans SC（OFL）裁 → **260 KB / 1262 字形**，并**同时产出 `charset.txt`**
让运行时按同一份清单烘焙（否则漏字就是空白，且极难发现）。

### 两个路径坑（会一直咬人）

| 坑 | 现象 | 解法 |
|---|---|---|
| 工程名 `gunmu party` 含空格 | `javac` 报 `无效的标记: D:/Downloads/gunmu` | 传给工具链的路径换成 **8.3 短路径** `D:/DOWNLO~1/GUNMUP~1`（ctypes 调 `GetShortPathNameW`） |
| 短路径只能对**已存在**的路径取 | 对输出文件取 → 产物名变成 `GUNMU-~1.JAR` | 产物先落在工作区，再普通拷贝到最终位置 |

### 宿主 Python 垫片的坑

- `shutil.rmtree` / `os.remove` 被劫持成"移到回收站"，回收站不可用就 fail-closed，
  甚至整个进程静默死掉 → 脚本里改自己走 `os.walk(topdown=False)` 并容忍失败。
- Java 18+ 的 `stdout.encoding` 跟随控制台代码页，重定向后变 `ms936` → 中文乱码。
  加 `-Dstdout.encoding=UTF-8`，Python 侧 `encoding="utf-8"`。

## 渲染崩盘复盘：为什么"全绿"还是交付了看不见的画面

用户反馈：「视角有问题，移动方向有问题，啥都有问题」。**他说的全对。**

我之前一直在用断言证明"它能跑"，但没有任何人（包括我）真的看过画面。
补上抓帧能力后，第一张截图就暴露了：**画面上 83.4% 的像素是清屏色，地面整片不存在。**
而它的编译、10 张地图硬校验、整局 5 关冒烟测试**全部通过**。

### 三个真 bug（都在 `MeshFactory` / `CameraRig`）

| # | 位置 | 现象 | 真因 |
|---|---|---|---|
| 1 | `MeshFactory.terrain` 三角形绕序 | **整片地面消失** | 绕序 `0→1→2 / 0→2→3` 算出的几何法线是 **−Y**，而顶点法线是 +Y，正好相反 → 开启背面剔除后全部被剔掉 |
| 2 | `MeshFactory.box` 顶点位置 | 不是立方体，是六张纸片 | 位置只写成 `u·su + v·sv`，**漏了沿面法线的那一项**，六个面全落在过原点的平面上。墙 / 机关 / 护盾都是这个几何 |
| 3 | `MeshFactory.sphere` 绕序 | 球看不见 | 同上，`a,c,b + b,c,d` 是反的 |

另外两个"确实存在但不是主因"的问题也一起修了：

- **`short` 索引上限**：`Mesh.setIndices` 只吃 `short[]`，单网格顶点上限 65535。
  冰隙峡谷 ICE 组有 **67960** 个顶点 → 索引回绕撕图。改为 96 格一块切块（单块最多 ~3.7 万）。
  这条是真 bug，但**不是地面消失的主因** —— 修完它地面照样看不见。
- **相机完全错了**：`CAMERA_HEIGHT_ABOVE` 与 `CAMERA_DISTANCE` 叠加使用，
  屏幕中心落到玩家头顶 **9m** 处（玩家被顶出画面下沿）；
  `direction` 写死 `(0,sin,cos)` 与相机实际位置不匹配 —— **相机根本没看向玩家**。

### 移动方向：屏幕空间 vs 世界空间

`Hud.applyInput` 把 W 直接映射成世界 `−Z`，而相机看向 `+Z`
→ **按 W 是朝镜头方向退**。摇杆同理（`mz += -stickDelta.y`）。

正解：屏幕上方在世界里是相机的水平朝向 `(sin yaw, cos yaw)`，
屏幕右方是 `(cos yaw, −sin yaw)`；输入必须过这一层旋转。

### 相机重做（D33）

改成"绕看点环绕"，并把不变量写进代码注释与文档：

```
看点   = 玩家 + 赛道切线×LOOKAHEAD + 上×LOOK_LIFT
相机位置 = 看点 − 赛道切线×(DISTANCE·cos PITCH) + 上×(DISTANCE·sin PITCH)
相机朝向 = normalize(看点 − 相机位置)     ← 由位置反算，保证看点永远在屏幕正中
```

俯角 35° → **50°**，距离 17 → 22，朝向跟随**赛道切线**（不再是固定 yaw，
之字断崖那种折返图才不会被横着看）。实测 `dir=(0.00,−0.77,0.64)` 正好是 50°。

### 新增的三种"不用眼睛"的检查（D36）

| 检查 | 断言什么 | 抓哪个 bug |
|---|---|---|
| `PrimitiveTest` | 逐三角形几何法线朝外 + 包围盒三轴尺寸 | 绕序反转 / `box` 退化 |
| `TerrainAudit` | 10 张图逐面统计"朝上三角占比"，<98% 判失败 | 地形绕序 |

**关键点**：`TerrainAudit` 复用渲染器同一条代码路径（把 `collectTerrainTile` 抽成不碰 GL 的纯函数），

## 追加：A/D 左右反了（用户的第二条反馈，也是真 bug）

用户原话：「为啥按下 a 会往右边按下 d 会往左边，反了吧」——**又是对的。**

### 根因：屏幕右方向的符号写反

libGDX 的 `Matrix4.setToLookAt(eye, target, up)` 里：

```
z_view = normalize(eye − target)     // 相机看向 −z_view
x_view = normalize(up × z_view)      // 屏幕右
```

代入 `up = (0,1,0)`、水平朝向 `f = (sin yaw, cos yaw)`（`z_view = −f`）：

```
x_view = up × (−f) = (−f.z, 0, +f.x) = (−cos yaw, 0, sin yaw)
```

我之前写的是 `wx = fx·sy + fz·sx`、`wz = fz·sy − fx·sx` —— **横向两项符号全反**。
yaw=0 时按 D 得到 `+X`，而屏幕右其实是 `−X`。纵向（W/S）没写错，
所以症状正好是"只有左右反"。

正确：

```java
out.x = fx * sy - fz * sx;
out.z = fz * sy + fx * sx;
```

### 抽成纯函数 + 用相机自己的基向量验证（D38）

新的 `core/InputMapping.screenToWorld(camYaw, sx, sy, out)`，
配套 `tools/InputMappingTest`：

- 对 10 个朝向建**真实的** `PerspectiveCamera`，从它的视图矩阵里取第 0 行（屏幕右）
  与第 1 行（屏幕上）的水平分量当**权威参照**；
- 断言 `按 D` 与屏幕右的点积 ≈ +1，`按 W` 与屏幕上的点积 ≈ +1。

**验过这条断言不是摆设**：把符号改回错误版本，10 个朝向的 `D→右` 点积全部变成
**−1.0000**，而 `W→上` 仍是 +1.0000 —— 精确复现"只有左右反"。

踩到的附带坑：`PerspectiveCamera.update()` 会走 `Frustum.update()`，
里面 `Matrix4.prj` 是 **native** 的，无头环境不加载 gdx 原生库会
`UnsatisfiedLinkError`。解法是测试开头 `GdxNativesLoader.load()`（不需要窗口/GL）。

## 第二批反馈（4 条），逐条落地

用户原话：地图每关都固定 / 存档点该是过区域就存 / 玩家下面有块草的圆形地板 / 机关没跟坡度对齐会穿模。**四条全对。**

### ① 地图固定 —— 断言直接抓到了真 bug（D39）

先加了 `MapPickTest`：48 个种子各建一局，统计第 1 关抽到几种图。

```
修复前：48 个种子共抽到 1 张不同的第 1 关地图（竞速池共 4 张）
修复后：48 个种子共抽到 4 张不同的第 1 关地图
```

根因是 **`java.util.Random` 对相邻小种子的高位几乎不变**。实测
`new Random(s).nextInt(4)` 在 s=1..6 时**全都是 2** —— Random 的构造只是
`seed ^ 0x5DEECE66D` 再线性同余，加 1 只让乘积变化约 2^38，而 `nextInt` 取高位，
2^38/2^17 才动到高位的一小段，取模 4 后落进同一个桶。

修法：交给 `Random` 之前先做 **murmur3 雪崩混合**（`LevelDirector.mixSeed`）。
另外一局之内**赛道图不重复**（`usedMaps`）。

**同时承认**：我以前把 `-Dgunmu.seed=20260921` 写进了 README 的"怎么跑"里。

### ④ 机关贴合坡度（D41）

## 第三批反馈（2 条）

### ① 跳跃整条链路是断的（D43 / D44）

用户原话：「怎么还是没法跳跃」。查明 `input.jump` **只有两处写入**（`Hud`、`BotBrain`），
**全仓零处读取** —— `GameConfig.JUMP_VELOCITY` 定义了也从没被用过。
对比 `useItem` → `ItemSystem`、`useUltimate` → `UltimateSystem` 都是"读一次 + 清掉"，
唯独跳跃没有消费者。`RollInput.clearEdges()` 也同样从未被调用。

修法（`PhysicsWorld.stepOne`，放在重力之前）：

```java
if (r.input.jump) {
    r.input.jump = false;              // 边沿信号：读到即消费
    if (r.canJump()) {
        jumpCount++;
        r.vel.y = GameConfig.JUMP_VELOCITY * r.jumpMultiplier();
        r.grounded = false;            // 起跳当帧就离地
    }
}
```

外加 `resolveGround` 加一条：**上升中（`vel.y > 0.01`）绝不贴地**（D44）。
否则起跳当帧的上升位移（5.4/60 = 0.09）若小于 0.06 的贴合余量，会被同一步按回地面。

**新增断言 `JumpTest`**（平地跑真实物理，7 项检查）：起跳初速 = `JUMP_VELOCITY − GRAVITY·dt`、
当帧离地、边沿被消费、无二段跳、腾空高度对得上 `v²/(2g)`（实测 0.867m vs 理论 0.911m，误差 4.9%）、
滞空 37 帧 vs 理论 41 帧、落地可再跳。
**反证过**：把消费点临时屏蔽 → 输出 9 项失败（`vel.y=0.000`、`腾空高度 0.000m`、`滞空 1 帧`）。
整局冒烟再加一条累计量断言：`PhysicsWorld.jumpCount` 必须 > 0（实测一整局 AI 跳 352 次）。

### ② 掉进虚空能偷到存档点与终点（新决策见 docs/06）

用户原话：「之字断崖跳到虚空里时能直接读取到下面的存档点和通关区域，
因为销毁不是瞬间销毁的」。

根因：进度是 `route.nearest(x, z)` 算的 —— **只看水平坐标，完全不看高度**。
折返型赛道（之字断崖）在俯视图上两段路靠得很近，脚下一空掉进虚空时最近点会跳到
"更靠后"的那一段，弧长瞬间跳几百米；而坠落判定要等掉够几米才生效，这段时间足够把
存档点与终点判定全部误触发。**地形也是用同一个 `nearest` 裁出来的**，所以连地形本身
都带着这个歧义。

**修法**：新增 `map/TrackProgress`（运行时与审计**共用同一份实现**，D36 原则）。
弧长只在同时满足三条时才成立：脚下可行走、横向不出走廊（`|lat| ≤ hw + sh`）、
高度对得上该处路面（含路肩每往外 1 米下降 0.42 的坡）。
并且分别用「水平最近段」与新的「含高度最近段」（`Route.nearestTrack`）各试一次，
前者与地形口径一致、后者解决叠层赛道。读不到就**冻结上一次弧长**（不前进也不后退）。
注意 `Route.nearest` 本身**不许改** —— 改它等于改所有地图的几何。

**新增断言 `RouteAudit`**：对每张竞速图**模拟坠落**（每个虚空格子，从旁边路面高度往下落 20m，

## 第四批反馈（2 条）：起点屏障 + 道具属性显示

### ① 开局 8 秒起点屏障（D46）

需求原话：「8 秒之前所有人都被困在起点区域内，8 秒后这层屏障消失，
在被困住的期间可以随便移动」。这句话里有**两条互相拉扯**的约束 —— 出不去 ∧ 随便动。
只做第一条很容易写成"开局把所有人钉死原地"。

实现：

| 层 | 做法 |
|---|---|
| 区域 | 由出生点**推导**：中心 = 形心，半径 = 最远出生点 + 3.5m（下限 11m）。三种模式的出生点布局（竞速方阵 / 生存环形）完全不同，手写必然漂移 |
| 硬校验 | `MapValidator.validateStartZone`：出生点全在内、中心脚下可行走、半径不低于下限（失败直接抛异常） |
| 物理 | 圆柱，**不限高**；只钳制位置 + 抹掉朝外的速度分量（不是弹开）。弹开会把人反复推来推去，"随便移动"就没了 |
| 时钟 | 屏障期间**比赛时钟与生存关危险区都不推进**。否则每个子图白扣 8 秒 |
| 渲染 | 半透明青色圆筒（新几何 `MeshFactory.tube`，**双面**——人在筒里，只画朝外的面会被背面剔除掉）+ 地面基环 |
| HUD | 顶部中间「起点封闭 x.xs」倒计时。屏障是"看不见摸不着但就是出不去"的东西，**必须给倒计时**，否则玩家只会觉得游戏卡住了 |

`tube` 的绕序推导：外表面三角形 `(T_i, T_{i+1}, B_i)` 的 `u × w` 正好是 +径向，
内表面反向一份。双面用两份顶点实现（法线一份朝外一份朝内），半透明叠两层正好读成能量墙。

### ② 道具属性显示不全（D47）

用户原话：「道具属性的显示范围太小了应该要显示完整属性」。

根因两层：
1. 旧实现是**一行且不折行**（`道具 名字 — 说明`），中文长句被屏幕右边缘切掉；
2. 中英文混排的折行**不能交给 `GlyphLayout`** —— 它按**空格**断词，
   中文整句没有空格，会被当成一个超长单词原样溢出。

改成一张道具卡：名称（稀有度配色）/ 稀有度 / 作用对象 / 持续 / **完整说明（按字折行）** / 梗出处。
折行算法抽成纯函数 `Fonts.wrapText(text, width, advance)` —— 只依赖"每个码点多宽"，
所以**不需要 FreeType 与纹理就能无头断言**。

断言三条可证伪的性质（`TextWrapTest`）：折行**无损**（拼回一字不差）、**不溢出**、
**真的折了**（除末行外每行接近满宽，否则就成"每行一个字"了）；外加标点不落行首、空串/零宽边界。

### ③ 一个伪装成"玩法回归"的测量口径问题

加完屏障后整局数据突然从「均 611m / 死亡 0」变成「均 554m / 死亡 9」，看起来像把玩法改坏了。

真因：**探针自己有个"每关 3600 帧"的硬性上限**，而屏障那 8 秒也算在里面 ——
等于在"比赛时间少 8 秒"的前提下测平衡。把上限改成 `ticksPerStage + START_BARRIER_TIME/FIXED_DT`
之后回到「均 604m / 最好 618m（触到终点）」，历时也从 60.3s 变成 68.4s。

教训：**加了"不计入时长"的机制之后，所有按帧数计量的测量都要同步校准**，
否则你会在一个假回归上查半天。

## 第六批：生存图直接崩进程（NPE）

用户贴的堆栈：

```
[Terrain] 地图 涨水盆地 · 高度场 119x119 · 6 块，单块最多 22920 顶点
[GunmuParty] 进入第 3 关 · 涨水盆地 · 控制方式：玩家
Exception in thread "main" java.lang.NullPointerException:
    Cannot read field "totalLength" because "<local3>.route" is null
  at LevelScreen.logDiagnostics(LevelScreen.java:181)
```

### 根因

`MapDef.route` 是**折线赛道路径，只有竞速图有**；生存图 / 竞技图是找路 / 环形场地，
`route == null`。而诊断行里写了一句裸的 `route.totalLength` —— 一进生存图就炸。

先把全仓 `route` 解引用审了一遍：**只有这一处漏判**，其余（`BotBrain.thinkRace`
及其两个 helper、`LevelDirector` 的 RACE 分支、`SceneRenderer` 的存档带）都在 RACE 路径内。

### 修法（不只是补一个判空）

难点在于**代码在 `LevelScreen` 里 —— 要开窗口才跑得到，单元测试够不着。**
所以做了三件事：

1. **唯一判空口径**：`MapDef.hasRoute()` / `routeLength()`；新增 `map/MapNav` 收拢
   "按模式有条件成立"的查询（`cameraYaw` / `progressText` / **`diagLine`**）。
2. **连那行诊断文本都抽成纯函数**，于是可以对 10 张图逐一无头跑 —— 崩的那一行本身被覆盖了。
3. **源码级检查**（`tools/run_smoke.py` 编译前）：任何 `.route.` 解引用必须同行带守卫
   （`hasRoute(` / `routeLength(` / 空判断）或挂 `// route-ok: 原因`，否则直接构建失败。

第 3 条一上线就抓出 **5 处**（3 处真该改，1 处是注释里的字样误报）：

| 位置 | 处理 |

## 第七批反馈（3 条）：生存关操控、AI 乱动、之字断崖

用户原话：「为啥在生存关卡我无法操控自己，所有AI都一直在前后乱动，
而且之字悬崖根本没办法通关，一到终点就被瞬移到上面而且还是能偷鸡」。

### ① 根因是一条**循环写反**（D53）——影响所有地图

`extendPads` 往起点前面插 3 段缓冲台：

```java
// ❌ 原来
for (int i = 3; i >= 1; i--) route.nodes().insert(0, first - u * 12f * i);
// 得到 [first−12, first−24, first−36, first] —— 先往回走 36 米，再猛跳回起点
// ✅ 现在
for (int i = 1; i <= 3; i++) route.nodes().insert(0, first - u * 12f * i);
// 得到 [first−36, first−24, first−12, first] —— 一路延伸出去
```

**后果不是"多绕一点路"**：折返段与后面的路**在空间上完全重叠** → `nearest` 在两条弧长
之间乱跳（偷鸡），出生点被摆到折返段上、脚下一会儿是起点高度一会儿是中段高度。

实测（青丘缓坡）：段长本该 12/12/12，实际 **10.4 / 10.4 / 31.2**（31.2 = 36×k，就是那一跳）。

修好后，**所有竞速图的出生点 `arcAt` 从"读不到/44.6"变成整齐的 `0.00`**。

### ② 之字断崖：终点层压在中段正上方（D54）

`RouteOverlapTest` 一跑就露出来了 —— 原来 8 处相交，最狠的一条：

```
段9↔段21 水平距 0.0m  高度 120.0 vs 6.0  差 114m
```

**水平距离 0.0 米、高度差 114 米** —— 终点层正压在中段正下方。
地形"按离最近路段逐格定高"，一个格子只能存一个高度 ⇒ 高的那条盖住低的
⇒ 玩家跑到终点（y=6）时 `resolveGround` 把他抬到 y≈120。

**这就是"一到终点就被瞬移到上面"的精确机制。**

起点 (0,150,−280) 也压在中段 (8,100,−296) 头上，**出生点直接落进中段地形**
（出生点 y=123，而起点路面 150）。

修法：**之字断崖重排成"一路向下的之字形"**（终点在路径末端，不再折返回中段），
每条横向带子之间留 ≥ 90 米 z 间距。4 张图现在 0 处相交，最小余量 8.5m。

### ③ 进度判定两处非平凡修正（D55）

| 问题 | 修法 |
|---|---|
| 弯道处两条边等距 → 最近段来回切 → **一帧跳十几米**（而滚木一帧最多走 0.37m） | 加**段滞后**：`arcAt(..., hint)` 优先沿用上一帧的段及其邻居 |
| 拿钳制后的 `t` 算弧长 → 走到段末外时弧长**卡住**，越界后一次性补回 `0.25×段长 ≈ 9m` | **弧长按未钳制的 t 外推**（投影点仍用钳制值算横向距离） |

修完：之字断崖 **冻结帧 964 → 9**、**跳变 382m → 22m**，4 张图**全部 55~65 秒跑完**（时限 300s）。

### ④ AI"前后乱动"是 AI 自己的锅（D56）

`steer()` 永远全油门朝目标冲。滚木有惯性（摩擦 1.0/s，9 m/s 刹车要 9 米），
到了目标停不下来 → 冲过头 → 目标落到身后 → 掉头冲回来。修法：按 `v²/MOVE_ACCEL`
估刹车距离，进入该半径后按距离比例收推力。

### ⑤ "生存关无法操控自己" —— 证据表明是**坡度**，不是 bug

`MoveControlTest` 走和游戏同一条链路（屏幕输入 → `InputMapping` → `PhysicsWorld.step`）：

```
青丘缓坡 竞速 输入 6.0s 前进 54.29m（方向误差 0.1°）
涨水盆地 生存 输入 6.0s 前进 51.44m（方向误差 9.0°）
收缩木桩林 生存 输入 6.0s 前进 52.27m（方向误差 0.2°）
锯盘深井 生存 输入 6.0s 前进 51.79m（方向误差 0.6°）
决斗坑 竞技 输入 6.0s 前进 51.32m（方向误差 7.0°）
```

**三种模式都能操控。** 而"松开输入 1 秒后仍有 8.3 m/s"是因为生存图是**碗形场地**，
滚木在坡上本来就会继续往下滚（摩擦正常生效、材质 GRASS 摩擦 1.0）。

**我一度把这条当成"输入没被消费"的证据 —— 那是误伤。**
判据应该是"输入有效"（能动 + 方向对），不是"松开就立刻停"。

### ⑥ 假探针会伪造结论（本次最重要的教训）

`RaceRunTest` 的"理想驾驶员"用 `progress` 算目标点，而 `progress` 只增不减 ——
判定一旦短暂滞后它就定住，目标点落到玩家身后，车在原地打转，
**于是探针报出"之字断崖跑不完"这个假结论**，我差点据此去改地图。

改成"上一帧读到的弧长 + 前瞻"后，同一张图 55 秒跑完。

**同类问题今天出现三次**：探针口径错（每关帧预算、子系统计数、目标点基准）。
**看到"回归"先问一句：是玩法变了，还是我的尺子变了？**

### 版本号唯一来源 = `GameConfig.VERSION`（D31 的延伸）

本工程不走 Gradle 打包，**没有"一处配置两边生效"的机制** —— 于是版本号很容易漂移成
"APK 里写着 1.0.0、游戏大厅里写着 a0.0.1"。所以：

- 唯一源：`core/.../GameConfig.java` 的 `VERSION = "a0.0.1"` / `VERSION_CODE = 1` / `VERSION_STAGE = "内测版"`；
- 统一读取入口 `tools/version.py`：正则读源码，**读不到直接抛异常（不猜）**，
  并核对 `build.gradle` / `android/build.gradle` 的版本有没有漂移（不一致打告警）；
- 消费点三处都取同一份：安卓清单 `versionName`（`build_apk.py` → aapt2 link）、
  jar 文件名（`build_jar.py`）、**大厅界面显示的版本号**（`GameConfig.versionText()`）。

### 产物命名：带版本 + 固定别名

每次构建产出两份**内容相同**的产物（MD5 已核对一致）：

```
dist/gunmu-party-a0.0.1.jar        + 别名 dist/gunmu-party.jar
build/apk/gunmu-party-a0.0.1.apk   + 别名 build/apk/gunmu-party-debug.apk
```

带版本号的用于归档/分发，不带版本号的是"当前最新"的固定路径（README、adb 命令、
既有文档都按那个名字引用，不会因为升版本就要改一堆文档）。

### 顺手修掉的两处陈旧文案

- **大厅按键说明漏了 `Shift` 加速与 `J` 攻击**（上一批加了这两条却没更新大厅），
  抽屉按钮说明还写着"右下三个按钮"，实际早已是五个；
- 大厅新增**版本号显示**（标题下方 `版本 a0.0.1 内测版`）—— 内测玩家报 bug 时，
  "你玩的是哪一版"是第一个要问的问题，写在界面上比靠人问可靠。

### 新增文件

- `tools/version.py`（版本唯一读取入口 + Gradle 一致性核对）
- `CHANGELOG.md`（版本命名规范 + a0.0.1 首个可玩构建的完整内容 + 待观察项）

### 验证

- `aapt2 dump badging`：`versionCode='1' versionName='a0.0.1'`、label「滚木派对」、minSdk 26 / targetSdk 36 ✓
- `apksigner verify` 通过；APK 3.18 MB；jar 9.9 MB
- 冒烟全绿（字体字形 1499 → **1500**，因为多了"版本/内测版"等字）

### 教训（写进 MEMORY）

> 🔴 **构建脚本里的版本号、安卓清单的版本号、界面上显示的版本号，必须是同一份数据。**
> 不走 Gradle 的工程尤其危险：三处各自写一个常量，第一次升版本就漂移，
> 而漂移的后果是"内测玩家报的 bug 无法定位到具体构建"。

## 第六批：固定签名（项目自有 keystore）

用户原话：「以后使用固定签名，把生成的前面(签名)保存下来以后都用同一个签名」。

### 之前的问题

`build_apk.py` 用的是 `build/debug.keystore`（从 `~/.android/debug.keystore` 拷来）。两条硬伤：

1. `~/.android/debug.keystore` 是**每台机器各自生成**的 —— 别人 clone 源码打出来的包
   与你的包**签名不同**，同包名互相装不上（`INSTALL_FAILED_UPDATE_INCOMPATIBLE`）；
2. 拷到 `build/` 下的那份还在 `.gitignore` 里（`build/` 是构建产物目录，不入库）
   —— 清理一次、换台机器就没了，下次打出来的包就是**另一把钥匙**，
   而"已安装用户无法升级"这件事不会当场报错，只会在用户升级时炸。

### 做法

- 用 `keytool` 生成项目自有签名：`keystore/gunmu-party.jks`（PKCS12）
  - 别名 `gunmu-party`，storepass/keypass 均 `gunmu-party`，RSA 2048，**有效期 10000 天**
    （2026-09-21 → 2054-02-06）
  - SHA-256 `9378eae8 8974 3964 24fb f226 f86c ff63 f21e 014b 1050 38d9 cbc3 5054 c4f1 c7f5`
  - SHA-1 `df9ec163 8d08 3d45 499b 213e afe2 d13b 8190 4dc6`
- `keystore/README.txt`：**把密码与指纹写下来**（这是刻意的 —— 用户要"以后都用同一个"，
  那就必须让密码不可能被忘记），并写明"丢了 = 已安装用户永远无法升级"、
  备份要求、核对命令、重建命令（含"重建出来的是另一把钥匙"的警告）。
- `tools/build_apk.py`：改为默认用固定签名，参数 `--keystore/--ks-pass/--ks-alias` 可临时覆盖；
  **找不到就 SystemExit，绝不回退 debug key**（静默回退会打出一个"看着正常、装不上"的包）。
- `android/build.gradle`：新增 `signingConfigs.fixed`，debug 与 release 都指向它
  （Gradle 那条路本机跑不动，但配置不能缺 —— 别人用 Gradle 打也必须同签名）。
- `.gitignore`：加显式 `!keystore/*.jks`，并写明"将来不要用 `*.jks` 通配忽略密钥文件"。
- 文档：README 新增「签名（固定）」节（含 SHA-256 与"旧 debug 包要先卸载"）、
  docs/05 §9.2、CHANGELOG a0.0.1 补「从本版开始：固定签名」。

### 验证

- 重打 APK：`apksigner verify --print-certs` 输出
  `Signer #1 certificate SHA-256 digest: 9378eae8…c7f5` = keystore 指纹 ✓
- 产物仍是 `gunmu-party-a0.0.1.apk` + 别名 `gunmu-party-debug.apk`（3.18 MB）

### 教训（写进 MEMORY 与技能）

> 🔴 **签名不能放在构建产物目录，也不能用机器自带的 debug key。**
> 它是"身份"，必须入库 + 备份 + 密码可查；判断标准很简单：
> **换一台机器 clone 下来打出的包，能不能覆盖安装到同一台设备上？** 不能就是签名没固定。
>
> ⚠️ 切换签名是不可逆的：旧签名（debug key）签的包在设备上必须先卸载
> （`adb uninstall top.gunmu.party`），这条要写在更新日志里，否则内测用户会以为"装不上 = 游戏坏了"。

## 第七批：安卓版一打开就闪退（D62 / D63）

用户贴来的堆栈：

```
java.lang.NoClassDefFoundError: Failed resolution of:
    Landroidx/core/view/OnApplyWindowInsetsListener;
  at com.badlogic.gdx.backends.android.AndroidApplication.init(AndroidApplication.java:186)
```

### 根因

libGDX **1.13.5 的安卓后端运行期依赖 `androidx.core`**（`AndroidApplication.init()` 处理
edge-to-edge 用 `ViewCompat.setOnApplyWindowInsetsListener`），而我们的打包走自建工具链，
`CP_JARS` 里手抄了 4 个 jar —— androidx 一个都没有。

**为什么所有检查都是绿的**：javac 不需要解析 `AndroidApplication.init()` 方法体里引用的类
（`AndroidLauncher` 只调它的公开 API）⇒ 编译通过；d8 只做 class→dex 转换、不做链接检查
⇒ dex 生成成功；签名当然也成功。**只有真机启动那一瞬间才炸。**

### 修法（三步，全部落进脚本，不靠记忆）

1. **`tools/fetch_libs.py`：安卓运行期依赖闭包**
   - 来源改为 `.module` 的 **`java-runtime` variant**（不是 pom：pom 里混着 lint /
     annotationProcessor 条目，照它递归会拉出 `lifecycle-compiler`、
     `lifecycle-livedata-core-ktx-lint`（**构件根本不存在，直接 404**）、guava、rxjava……）
   - **白名单闸门**（`androidx.*` + 少数 artifact）：不加闸门实测拉出 60 个构件 24 MB
     （coroutines 的 debug/rx/javaFx/slf4j 变体、play-services、support-v4）
   - **下载前**做版本对齐（同逻辑构件只留最高版本）+ 补 `-jvm` 实现变体
     （`annotation-1.8.1.jar` / `collection-1.4.2.jar` / `kotlinx-coroutines-core-1.6.4.jar`
     本体**一个 class 都没有**，实现全在同版本 `*-jvm` 里）
   - 结果：`libs-mobile/` 23 个 jar / 5.8 MB（删掉目录重跑能**原样重现**，已用 diff 验证）
2. **`tools/build_apk.py`：库的 R 类**（AGP 3.0 之后不再随 AAR 分发）
   - `compile_library_resources()`：解各 AAR 的 `res/` → `aapt2 compile` → 与自己的资源一起
     `link`，并用 `--extra-packages` 为 8 个包生成 `R.java`（`androidx.core`、
     `androidx.lifecycle.runtime`、`androidx.arch.core`、`com.badlogic.gdx.backends.android`…）
   - `CP_JARS` 改成「基础 jar + `libs-mobile/` 目录扫描」——**不许再手抄**
3. **`tools/verify_dex.py`（新增，D62）**：解析 dex 的 `type_ids`（被引用类型）与
   `class_defs`（已定义类），断言"被引用的类 ∈ dex 定义 ∪ android.jar ∪ java 运行时"。
   - 对**修复前**的包：精确报出 5 个缺类（头两个就是 `OnApplyWindowInsetsListener` / `ViewCompat`）
   - 对修复后的包：0 缺类 + 2 条**写出理由的豁免**（`androidx.fragment.*` 只有
     `AndroidFragmentApplication` 用；`com.badlogic.gdx.backends.android.R$*` 只在软键盘
     输入对话框的内部类里用，本作无文本输入）
   - 还有 **`MUST_DEFINE` 正向断言**（缺类扫描是减法，万一引用被删掉它就"无话可说"）
   - 已是 `build_apk.py` 第 7 步：**校验不过就中止构建、不产包**

产物：`gunmu-party-a0.0.1.apk` **3.18 → 5.02 MB**（多的是 androidx + kotlin + coroutines
运行期依赖；Gradle 打的 debug 包同样含它们，release 经 R8 才会小）。签名指纹不变 ✓

### 这一轮踩的坑（都值得记）

1. 🔴 **沙箱只放行 curl，不放行 Python 的 socket**：`urllib` 一律 `WinError 10013` 或超时，
   而 `curl` 拿同一个 URL 是 200。⇒ `fetch_libs.py` 的 `http_get()` 加 curl 回退，
   否则"依赖下载"这种事在受限环境里根本做不了。
2. 🔴 **宿主拦"批量删除"**：`os.remove` 一轮超过约 50 个就整体拒绝（`SAFE_DELETE_BULK_CONFIRM_REQUIRED`，
   count=142/threshold=50），于是"下完再清理"的做法会把重复版本的同一个库留在目录里，
   而 **d8 遇到两个 jar 定义同一个类是直接报错的**。⇒ 把版本对齐**前移到下载之前**，
   只下该下的；清理只做兜底并容忍失败。
3. 🔴 **`python ... | tail -30` 会让人以为进程卡死**：管道要等命令结束才输出，长任务看起来就是"没反应"。
   ⇒ 长命令一律 `> build/xxx.log 2>&1` 再 `tail` 读日志。用户为此说了一次"你都卡死了"。
4. **依赖"本体为空壳"**：Gradle 的 `available-at` 语义在 `.module` 里不是一条普通依赖，
   只按依赖列表下会漏掉实现。

### 教训（写进 MEMORY / 技能）

> 🔴 **"编译通过 + 打包成功 + 签名有效"证明不了"能启动"。**
> 运行期依赖（尤其安卓的 androidx）必须有一条**能静态计算**的断言兜住：
> dex 里被引用的类，要么在 dex 里、要么在框架里、要么在 java 运行时里 —— 这个判据不需要真机。
